# Project Audit — 2026-08-24

This file records the initial consistency audit between the project conversation, the imported Rust weakness inventory, the GitHub Issues, and the repository documentation.

## Confirmed project invariants

- The project aims to improve Rust's weak areas without discarding Rust's core safety/performance model.
- The user-facing language direction is intentionally inspired by Lua minimalism, Python readability/rapid expression, and Rust systems semantics, with a goal of being simpler to write than all three where practical.
- The initial implementation strategy is a front-end/transpiler that lowers Evolution source to Rust, then uses rustc/LLVM for native code generation.
- Correctness is a prerequisite for performance comparison.
- Runtime performance is a hard gate: for equivalent semantics and controlled conditions, `T_evolution <= T_reference_rust`.
- Ergonomic gains, compile-time gains, or shorter source do not compensate for a repeatable runtime regression.
- Hidden allocations, clones, boxing, dynamic dispatch, a mandatory GC, or a heavy runtime are not acceptable default costs for ordinary syntax sugar.
- Safety regressions are not accepted as performance wins.
- Benchmark comparisons must use equivalent work, equivalent inputs, controlled build/runtime conditions, repeated samples, and anti-optimization safeguards.
- The complete Rust weakness inventory is preserved in issue #6 and summarized in `research/WEAKNESS_MAP.md`.
- Work is organized through branches, PRs, tests, and CI; failed experiments are documented rather than erased.
- Duplicate active GitHub Actions runs for the same SHA/workflow/input are not to be created; the active run is tracked while independent work continues.
